# Spec v1.1 Supplement: Goal-Driven CamFlow

Status: supplement to v1.1, not a replacement for `docs/spec.md`
Date: 2026-05-05

This document narrows the goal-driven extension to the semantics CamFlow
actually needs now. It keeps v1.1 stable: no new runtime class, no
`state:`/`inputs:`, no user-node sub-workflows, no unbounded retry, and
no default human gate.

## 1. Existing Compatibility

CamFlow v1.1 already has the right vocabulary:

- `Workflow.goal`: the top-level objective for the compiled workflow.
- `Node.goal`: the local objective for one atomic node.

Therefore goal-driven execution does not require a new YAML concept. It
requires using the existing goal fields more deliberately.

## 2. One Active Execution DAG

The user-facing model is one active execution DAG.

- Fresh run: Planner creates execution DAG revision 1 from the prompt.
- Replan later: Planner may create execution DAG revision N+1 from the
  same original objective plus run evidence.
- Runtime always executes one active DAG revision at a time.

The builtin Planner workflow is still a real CamFlow workflow, but it is
an internal compiler workflow. It should not become a second
application-level DAG in the user's mental model.

## 3. Must Keep Now

These are the minimum semantics to absorb the Ralph/Goal idea without
destabilizing v1.1.

### 3.1 Workflow Goal Is The Objective

`Workflow.goal` is the persistent objective for the run. Retry, review,
and final audit should be judged against this goal, not only against the
last local error.

The original user prompt remains the external source of truth.
`Workflow.goal` is the Planner's compiled restatement of it.

### 3.2 Node Goals Must Map To Workflow Goal

Every non-trivial `Node.goal` should explain what part of
`Workflow.goal` the node advances or proves.

This is a Planner responsibility. The first implementation can enforce
it through Planner prompt discipline and sentinel tests, not runtime
schema changes.

### 3.3 Retry Is The Inner Goal Loop

Current v1.1 retry already passes `input.previous` to the next attempt.
The supplement only tightens the retry instruction:

- re-read `Workflow.goal`;
- re-read `Node.goal`;
- use `previous.feedback` as evidence about what is still missing;
- fix the local gap if the plan is still sound;
- surface plan mismatch instead of looping on the same local error.

Retry remains bounded. More retries are not a feature. First-pass
success is still the ideal.

### 3.4 Final Audit Must Prove The Original Goal

Node success is necessary but not sufficient. A final reviewer/auditor
for non-trivial workflows should map the original objective to evidence:

- requirement or success criterion;
- node output, audit envelope, test result, or file reference;
- pass/fail judgment for that criterion.

For now this can be a normal final `Node` generated by the Planner. It
does not require a new workflow-level verifier.

### 3.5 One Active DAG, Versioned Over Time

Startup planning and later replanning are the same kind of operation:
Planner produces a DAG revision for Runtime to execute.

The active `.camflow/run/workflow.yaml` may change only through a
recorded DAG revision. Runtime should not execute an unrecorded plan.

### 3.6 Record Every Runtime DAG For Replay

Every execution DAG revision that Runtime runs should be copied before
execution:

```text
.camflow/run/
  workflow.yaml
  dag_revisions/
    0001/
      workflow.yaml
      manifest.json
    0002/
      workflow.yaml
      manifest.json
```

The initial MVP manifest can be small:

```json
{
  "revision": 1,
  "parent_revision": null,
  "reason": "initial_plan",
  "workflow_goal": "..."
}
```

For replans, add only what is known:

```json
{
  "revision": 2,
  "parent_revision": 1,
  "reason": "manual_replan",
  "source_trace_step": 17,
  "workflow_goal": "..."
}
```

Runtime trace events should include `dag_revision` when practical, so a
future replay tool can reconstruct which plan was active for each node
attempt.

## 4. Must Keep Later: Planned Semantics

These semantics should remain in the architecture plan, but should not
be required for the immediate implementation. They are the second
category: must preserve in design, implement after the MVP is stable.

They are also a version boundary. Implementing these semantics changes
CamFlow beyond the v1.1 goal-driven MVP and should be treated as the
next spec version or an explicit RFC, not as a quiet v1.1 patch.

### 4.1 Planner Logical Residency

Planner should become logically resident for the lifetime of a run.

This does not require a permanently running Planner LLM process. It
means CamFlow keeps enough Planner state and run artifacts for Planner
to be re-entered when workflow-level decisions are needed.

Planner's later responsibilities:

- remember the original objective;
- remember why the current DAG revision should satisfy it;
- inspect trace, halt artifacts, and node outputs;
- decide whether the current DAG is still sufficient;
- propose a revised DAG when the plan is structurally wrong.

The key point is ownership: user nodes do not launch sub-workflows and
do not independently redesign the DAG. Replanning belongs to the
top-level runtime/Planner relationship.

### 4.2 Halt-Time Planner Review

After a workflow halts, Planner can inspect run artifacts and recommend
one of:

- local retry is enough;
- human input is required;
- replan is required;
- the goal is not achievable under current constraints.

This should start as an advisory report or trace event, not automatic
plan mutation.

### 4.3 Manual Replan Revision

If Planner recommends replan, it may propose a new DAG revision.

The safe first version should require explicit user approval before the
active `workflow.yaml` is replaced. The new revision must be recorded in
`dag_revisions/` before execution.

### 4.4 Invalidation Rules

Before automatic replan, CamFlow needs clear rules for which prior node
outputs can be reused and which downstream nodes must re-run.

Until those rules exist, the conservative default is to re-run affected
downstream nodes.

### 4.5 Automated Replan

Automated replan should wait until manual replan is reliable. It must
preserve the same original objective, record the DAG revision, and keep
a clear audit trail of why the plan changed.

## 5. Post-v1.1 TODO

Keep these TODOs visible until they are either implemented in the next
spec version or explicitly rejected:

1. Define Planner logical residency precisely: what state is persisted,
   how Planner is re-entered, and which artifacts it reads.
2. Add halt-time Planner review as an advisory pass over `trace.jsonl`,
   `halt.json`, node outputs, `Workflow.goal`, and the active DAG
   revision.
3. Define manual replan revision: how a proposed `workflow.yaml` becomes
   the active DAG revision, and what approval is required.
4. Define invalidation rules for DAG revisions: which prior node outputs
   can be carried forward and which descendants must re-run.
5. Only after manual replan is reliable, consider automated replan with
   a recorded DAG revision and a clear audit trail.

## 6. Explicitly Out Of Scope For This Supplement

Do not introduce these in the first goal-driven implementation:

- new `goal.status` lifecycle values;
- token or wall-clock budget semantics;
- physically long-lived Planner LLM process as a first-step
  requirement;
- new runtime class;
- user workflow nodes that launch sub-workflows;
- unbounded retry or retry-as-progress scoring;
- automatic replan without a recorded DAG revision.

## 7. Regression Benchmark Asset

`examples/value-demo/` is the canonical scored regression benchmark for
this line of work. Keep its fixture, prompt, setup script, scorer, and
protocol in the repo so future Planner/runtime changes can be scored
against the same task and compared to prior runs.

The benchmark is not the spec, but it is the regression guard for the
spec's value claim: CamFlow should outperform a single `camc run` by
producing inspectable multi-step workflows with independent audit
evidence.

## 8. Implementation Guidance

This section is guidance, not extra spec semantics. The Developer may
choose different code structure if it preserves the requirements above.

### 8.1 Planner Prompt Changes

The first implementation should prefer prompt and sentinel-test changes
over runtime machinery.

Planner should generate workflows where:

- `workflow.goal` is a concrete restatement of the user's objective;
- each non-trivial `Node.goal` names the part of the workflow goal it
  advances or proves;
- final reviewer/auditor nodes are included for non-trivial workflows;
- audit/reviewer instructions require evidence against the original
  goal, not only a summary of node success.

This keeps the change close to the existing Planner work and avoids
changing the v1.1 YAML schema.

### 8.2 Retry Prompt Changes

Retry should use the existing `previous.feedback` channel. Do not add a
new retry state field for the first version.

The retry prompt or skill instructions should make the agent answer:

- what part of `Node.goal` is still unmet;
- how that gap affects `Workflow.goal`;
- whether the current plan is still sufficient;
- what local action will close the gap.

If the node cannot close the gap locally, it should fail clearly rather
than loop on unrelated edits.

### 8.3 Final Audit Shape

For now, final goal audit should be a normal generated node. It should
depend on implementation and independent audit/test nodes where those
exist.

The expected output can stay simple:

```json
{
  "approved": true,
  "issues": [],
  "per_requirement_evidence": []
}
```

The important part is the evidence discipline: every explicit
requirement from the original goal should have concrete supporting
evidence.

### 8.4 DAG Revision Recording

The first DAG revision implementation can be mechanical:

1. after Planner writes `.camflow/run/workflow.yaml`;
2. before Runtime executes user nodes;
3. copy that workflow into `.camflow/run/dag_revisions/0001/`;
4. write a small `manifest.json`;
5. add `dag_revision` to new trace events when easy.

This should not affect scheduling, retry, or verification behavior. It
is an audit/replay artifact first.

### 8.5 Tests

Use focused sentinel tests before broad runtime tests:

- Planner prompts mention workflow-goal to node-goal mapping.
- Retry instructions mention `Workflow.goal`, `Node.goal`, and
  `previous.feedback`.
- Final reviewer/auditor guidance requires per-requirement evidence.
- A fresh run records `dag_revisions/0001/workflow.yaml` before user
  workflow execution.

These tests should protect the goal-driven behavior without requiring
automatic replan yet.

## 9. Immediate Implementation Order

1. Strengthen Planner prompts so `workflow.goal` is clear and node goals
   map back to it.
2. Strengthen retry prompts/skills so retry is explicitly goal-driven.
3. Ensure final reviewer/auditor nodes cite evidence against the
   original goal.
4. Add DAG revision recording for the active workflow before Runtime
   executes it.
5. Only after the above is stable, add advisory halt-time Planner
   review.
